# Phase 2.7 Controlled Graph Cutover Preparation Design

**Status:** Draft for approval
**Date:** 2026-10-30
**Scope:** Safe development/test fixtures and isolated local environments only

## Intent

Phase 2.7 proves that the typed organization graph can reproduce legitimate legacy
organization behavior after canonical assignments are populated in a controlled
environment. It prepares, but does not perform, a future production cutover.

The required evidence sequence is:

```text
legacy → controlled canonical backfill → parity → shadow read → controlled graph read
→ rollback to legacy → cutover readiness
```

Production remains `graph_mode=legacy`. No global production backfill, legacy-storage
retirement, graph cutover, permission redesign, route change, navigation change, or
Phase 3 work is included.

## Goals

- Explain all four current access-loss differences and prove whether they are missing
  canonical assignments or graph-logic defects.
- Inventory and safely execute the ten deterministic proposals in isolated fixtures.
- Prove first-run creation, second-run idempotency, and zero-proposal third dry-run.
- Rerun parity after controlled backfill and stop if any legitimate mismatch remains.
- Formalize fail-safe `legacy`, `shadow`, and `graph` read modes.
- Support scoped activation without coupling graph mode to roles or permissions.
- Preserve legacy readers, legacy columns, compatibility writers, audit history, and
  rollback by changing read mode only.
- Provide structured shadow counters and a deterministic `READY`/`BLOCKED` health gate.
- Test graph-mode behavior and direct-access security boundaries across representative
  OASIS roles and modules.

## Non-goals and Anti-goals

- Do not write to production or run an uncontrolled/global backfill.
- Do not remove `users.supervisor_user_id`, `sales_coordinator_sales`, or compatibility
  writers.
- Do not make graph mode the production default.
- Do not grant capabilities through graph membership.
- Do not create a generic feature-flag platform.
- Do not redesign unrelated organization services, routes, navigation, or UI.
- Do not begin Phase 3.

## Current Evidence and Constraints

- Phase 2.6 verified 1,548 PHPUnit tests and 11,573 assertions.
- Current mode is `legacy`; no production cutover or global backfill occurred.
- Current diagnostics show four access-loss differences, zero expansions, zero unknowns,
  and ten deterministic dry-run proposals with zero writes.
- Typed relationships are `reports_to` and `sales_team_member_of`.
- Reporting traversal and Sales-team traversal remain separate.
- Permissions determine capability; organization scope determines record/entity reach.
- Existing code already has partial mode branches: reporting supports a shadow path,
  while other services inspect `config('organization.graph_mode')` directly.

## Chosen Approach

### Central `OrganizationGraphModeService`

Create one small resolver responsible for:

- normalizing configured mode to exactly `legacy`, `shadow`, or `graph`;
- accepting the existing `canonical` configuration value as a backward-compatible
  alias for internal `graph` semantics while preserving raw diagnostic metadata;
- defaulting missing, malformed, or unsupported configuration to `legacy`;
- resolving optional user and branch activation allowlists;
- returning the effective mode for a viewer without inspecting roles or permissions;
- exposing whether shadow comparison or graph authority is active;
- providing structured, bounded shadow comparison counters.

Existing organization readers will use this resolver at targeted seams. They will not
be rewritten behind a broad facade. `legacy` remains authoritative; `shadow` computes
canonical results and records aggregate diagnostics while returning legacy results;
`graph` returns canonical results while retaining legacy comparison data for rollback and
diagnostics.

### Scoped activation

Configuration supports a global mode plus optional allowlists:

- global mode: `ORGANIZATION_GRAPH_MODE`, default `legacy`;
- user allowlist: `ORGANIZATION_GRAPH_USER_IDS`, empty by default;
- branch allowlist: `ORGANIZATION_GRAPH_BRANCH_IDS`, empty by default.

Activation is environment/config-only for Phase 2.7. No UI or database activation flag
is introduced. User and branch allowlist matching uses OR semantics. A user match may
activate the mode for that user; a branch match applies only while evaluating a read in
that branch context, never as a blanket grant across all branches visible to the user.

The allowlist truth table is:

| Environment/context | Mode | Allowlist state | Effective result |
|---|---|---|---|
| Any | `legacy` | Any | Legacy |
| Local/testing | `shadow` | Empty or populated | Shadow diagnostics, legacy authoritative |
| Local/testing | `graph` | Empty | Legacy fail-closed |
| Local/testing | `graph` | Explicit user/branch match | Graph for the matched context |
| Local/testing | `graph` | No match | Legacy |
| Non-local/testing | `graph` | Any | Legacy fail-closed |

The resolver does not examine role slugs or permission grants. An empty allowlist never
activates graph mode. Outside tests, graph mode always requires an explicit user or
branch allowlist match.

The exact environment parsing will be centralized in `config/organization.php` and the
resolver. Invalid IDs or mode values resolve safely to legacy and produce health-gate
evidence rather than activating graph reads.

### Controlled backfill

Extend the existing backfill service/command with multiple independent explicit guards.
The write path must require all of the following:

- `APP_ENV` is `local` or `testing`;
- an explicit `--write` option;
- an explicit `--confirm-isolated` option;
- a non-production database identity/connection check;
- no production deployment/cutover marker;
- the requested fixture/selection is explicit and non-global.

Any failed guard rejects the write before mutation and leaves dry-run behavior intact.
The guarded path will:

1. report the four access-loss analyses;
2. inventory each proposal with source, target, typed relationship, branch/project,
   active/historical state, confidence, reason, and affected scopes;
3. write only deterministic, high-confidence proposals to the selected isolated DB;
4. preserve legacy rows and write typed canonical rows transactionally;
5. return before/after counts and proposal IDs;
6. remain repeatable without duplicate current assignments.

No command option may silently convert a normal production invocation into a write.

### Parity and health gate

Add a health-check service/command that combines:

- parity differences;
- unknown mismatches;
- access expansion/loss;
- cross-branch and cross-project expansion;
- reporting and Sales-team conflicts;
- cycle failures;
- backfill conflicts and idempotency results;
- typed-edge integrity violations;
- compatibility-writer synchronization health;
- mode configuration validity;
- shadow comparison counters.

The result is machine-readable and deterministic:

```text
READY    only when every required blocker is zero and controlled evidence is complete
BLOCKED  otherwise, with explicit reason codes
```

The existing parity gate remains authoritative for its dimensions; the new health gate
aggregates rather than suppresses or normalizes mismatches.

## Read-Mode Semantics

| Mode | Authoritative result | Comparison behavior | User-visible behavior |
|---|---|---|---|
| `legacy` | Legacy | Optional diagnostics only | Existing behavior |
| `shadow` | Legacy | Canonical is calculated and counters recorded | Existing behavior unchanged |
| `graph` | Canonical | Legacy remains available for comparison/rollback | Controlled cohort only |

Invalid configuration, failed graph integrity checks, missing activation context, and
unresolved ambiguous typed edges fail closed to legacy for the affected read. Graph mode
must never widen a scope when a comparison cannot be completed safely.

## Shadow Diagnostics

Shadow comparisons use aggregate structured records, not complete sensitive records.
Counters include:

- comparisons;
- exact matches;
- losses;
- expansions;
- unknown;
- branch mismatches;
- project mismatches;
- reporting mismatches;
- Sales-team mismatches.

Logs are bounded and keyed by module, relationship dimension, and viewer/branch context
where needed for investigation. PII and complete record payloads are excluded.

## Transaction and Compatibility Safety

Mutations that update legacy and typed representations use existing transaction and lock
conventions. A failure rolls back both representations. Compatibility writers remain
active for Supervisor changes, Coordinator changes, organization moves, and branch/project
assignment operations. Tests assert no partial legacy-only or graph-only success.

Canonical reads revalidate current account status, primary role, branch, project/workspace
constraints, and ambiguous same-type edges. Historical diagnostics may retain ended
relationships but never use them for current access.

The controlled fixture suite covers:

- modules: Sales leads, Sales Agenda, Work Planner, Consumer/KPR, Database, Dana

- invalid mode fallback;
- legacy, shadow, graph, scoped activation, and graph→legacy rollback;
- controlled backfill first/second/third idempotency checks;
- compatibility writer synchronization and transaction failure behavior.

## Future Production Stages

This phase only documents the staged path:

- Stage A: legacy reads plus graph diagnostics;
- Stage B: legacy authoritative plus shadow graph;
- Stage C: graph for a controlled internal cohort/branch;
- Stage D: broader controlled activation;
- Stage E: graph authoritative with legacy shadow;
- Stage F: legacy retirement considered only in a later dedicated phase.

Each stage requires explicit parity, security, rollback, and operational approval. Phase
2.7 ends with production `legacy` and a `BLOCKED` or `READY` evidence result; it does
not execute production cutover.

## Approved Decisions

- Phase 2.7 activation remains environment/config-only.
- No UI/database activation flag is introduced.
- Allowlists default to empty and fail closed to legacy.
- User/branch matching uses OR semantics; branch activation is limited to the branch
  context currently being evaluated.
- Graph requires an explicit user/branch allowlist outside tests.
- Controlled writes require multiple explicit isolated-environment guards.
- SAS and SAM are not invented as roles; they are included in the test/report matrix
  only when executable repository role definitions exist.
