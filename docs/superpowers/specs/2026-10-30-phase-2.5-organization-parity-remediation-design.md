# Phase 2.5 — Organization Parity Remediation Design

**Status:** Proposed — awaiting approval  
**Date:** 2026-10-30  
**Approach:** Evidence-gated remediation

## Intent

Bring the canonical organization graph closer to the intended legacy-effective
organization without making the graph production-authoritative. Phase 2.5 separates
three concerns that Phase 2 only reported loosely:

1. mismatch inventory and severity;
2. evidence-based remediation proposals;
3. an objective cutover gate that remains closed while critical differences exist.

The current development evidence contains one unambiguous proposed relationship and
four active dual-parent Sales conflicts. The four conflicts are same-branch and
same-workspace, but business intent is not provable from data alone; they must remain
unresolved rather than being assigned by precedence.

## Goals

- Classify every observed mismatch as security-critical, access loss, structural,
  historical, expected, or unknown.
- Surface access expansion (`legacy deny / graph allow`) separately from access loss.
- Enrich each mismatch with user, role, branch, project, active/historical state,
  source, severity, recommendation, and confidence.
- Correct only graph relationships supported by repository and data evidence.
- Make safe repair proposals additive, idempotent, auditable, and testable in isolated
  fixtures.
- Keep the production read source and all legacy compatibility writers unchanged.
- Block any future cutover while critical, unknown, expansion, conflict, or integrity
  gates remain open.

## Non-goals and anti-goals

- No graph read cutover or `graph_mode` default change.
- No production/global write backfill.
- No deletion, mutation, or retirement of legacy relationships.
- No automatic rule that Sales Coordinator mappings override legacy supervisors.
- No role, permission, route, navigation, or UI restructuring.
- No database constraints until actual data compatibility is proven.

## Approaches Considered

### Evidence-gated remediation — selected

Extend the existing parity/backfill tooling, then allow only explicitly approved
high-confidence additive repairs through a guarded service path. Keep ambiguous cases
as unresolved blockers. This preserves safety while making the canonical repair path
real and testable.

### Investigation-only

Would be safest operationally but would not provide a tested remediation mechanism for
the clearly proven missing-assignment category. It leaves the canonical graph unable to
progress even where evidence is sufficient.

### Broad conflict precedence — rejected

Making active `sales_coordinator_sales` override `supervisor_user_id` for all Sales
would hide four conflicts and change team ownership without a business decision. It
could create access expansion and is prohibited by the evidence-gated objective.

## Mismatch Assessment Contract

Every parity comparison will include:

- `severity`: `SECURITY_CRITICAL`, `ACCESS_LOSS`, `STRUCTURAL`, `HISTORICAL`,
  `EXPECTED`, or `UNKNOWN`;
- `access_direction`: `EXPANSION`, `LOSS`, `MIXED`, `NO_CHANGE`, or `NOT_APPLICABLE`;
- `confidence`: `HIGH`, `MEDIUM`, `LOW`, or `UNKNOWN`;
- `classification`;
- `suspected_source`;
- `recommended_resolution`;
- `evidence`: user/role/branch/project/source facts;
- `affected_modules`;
- `remediation_status`: `UNRESOLVED`, `PROPOSED`, `APPROVED_FOR_ISOLATED_TEST`,
  `REPAIRED_IN_FIXTURE`, or `BLOCKED`.

Direction is evaluated from effective record decisions, not only ID set differences:

- legacy deny / graph allow → `EXPANSION` and at least `SECURITY_CRITICAL` until
  explained;
- legacy allow / graph deny → `LOSS` and at least `ACCESS_LOSS` until explained;
- both sides contain IDs → `MIXED`; count the graph-only side as expansion and the
  legacy-only side as loss while retaining the unresolved classification;
- no reliable interpretation → `UNKNOWN`.

No mismatch may become equivalent because an ID was discarded or a conflict was
flattened.

## Safe Remediation Boundary

Add an explicit approved-repair service path around `OrganizationGraphService::assign`.
An approved repair must:

1. identify exact `user_id` and `parent_user_id` values;
2. re-read current legacy and graph state inside the operation;
3. require a high-confidence assessment and no active conflict;
4. revalidate role hierarchy, shared workspace, active status, cycle safety, and
   branch/project context;
5. be idempotent when the exact current assignment already exists;
6. write through `OrganizationGraphService` so legacy projection and audit behavior
   remain intact;
7. record source/reason as an approved Phase 2.5 remediation;
8. be covered by an isolated fixture write-then-repeat test.

There will be no command that applies all proposals to the configured/global database.
The existing `organization:backfill --dry-run` remains the only environment diagnostic
operation. Real-environment application requires a later explicit operational approval.

## Canonical Relationship Rules

The evidence package will document these as supported only where repository behavior
proves them:

- Sales → Sales Coordinator: a current `reports_to` graph edge may represent active
  team ownership only when no conflicting active mapping exists and role/workspace
  validation passes.
- Sales Coordinator → Supervisor: current graph parentage is valid only when role rank
  and shared workspace rules pass.
- Supervisor → Manager → Branch Manager: graph traversal follows current primary
  `reports_to` edges; role labels alone do not create edges.
- Branch membership: `branch_user` remains the workspace access source, with explicit
  current/historical state and primary fallback behavior preserved.
- Project membership: `project_user` remains date-valid operational assignment data;
  graph membership cannot grant a project by itself.
- Pusat visibility: retains existing explicit compatibility behavior and never becomes
  a system-wide graph inference.

## Sales Coordinator and Module Parity

The diagnostic will compare current and historical Coordinator mappings separately from
reporting hierarchy. It will exercise Sales lead, agenda, consumer handoff, and team
visibility decisions, and will flag:

- graph allow / legacy deny as critical expansion;
- legacy allow / graph deny as access loss;
- wrong Coordinator membership as a mapping conflict;
- historical mappings incorrectly treated as current as a historical integrity issue.

The same effective-decision comparison will cover Consumer/KPR, Work Planner,
Database, Dana Talangan, Pengeluaran, Reporting, and organization administration.

## Backfill Safety and Integrity

Phase 2.5 will verify two identical dry-run reports and an isolated approved-repair
write followed by a second run with no duplicate assignment. It will not execute a
global write backfill.

The future integrity contract will require no active self-parent, no active cycle, no
duplicate equivalent active primary assignment, valid source/target users, valid
branch/project context, and deterministic active reporting relationships where the
business rule requires one. Existing violations remain diagnostics until migration
compatibility is established.

## Cutover Gate

The parity command will expose a gate result that is `BLOCKED` if any of these are
non-zero:

- unknown mismatch;
- security-critical mismatch;
- graph access expansion;
- graph access loss that is not explicitly approved;
- cross-branch expansion;
- cross-project expansion;
- unresolved reporting conflict;
- unresolved Sales Coordinator mapping conflict;
- unclassified legacy anomaly;
- non-idempotent backfill;
- cycle/integrity failure.

The gate is diagnostic only. A `READY` result in a future phase would still require a
separate human-approved cutover operation.

## Rollback

Legacy-compatible reads and projections remain intact. If an isolated repair is later
approved and a problem appears, restore the legacy read configuration, retain the
audited graph history, and close/reverse the specific canonical assignment through the
existing graph service. No rollback depends on deleting legacy or historical data.
