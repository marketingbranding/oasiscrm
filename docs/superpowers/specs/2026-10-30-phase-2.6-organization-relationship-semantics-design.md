# Phase 2.6 — Organization Relationship Semantics Design

**Status:** Proposed — awaiting approval  
**Date:** 2026-10-30  
**Selected approach:** Typed canonical edges in `organization_assignments`

## Intent

Resolve the Phase 2.5 ambiguity without choosing a parent arbitrarily. Executable OASIS
behavior shows that formal reporting and Sales Coordinator membership are separate
business dimensions. Phase 2.6 will make that distinction explicit in the canonical
graph while preserving legacy reads, legacy columns, compatibility writers, and all
authorization boundaries.

## Evidence Summary

The current repository provides direct evidence that the relationships are orthogonal:

- `users.supervisor_user_id` is consumed by `ReportingHierarchyService`, formal
  descendant traversal, management hierarchy, supervisor monitoring, user administration,
  and hierarchy validation.
- `sales_coordinator_sales` is consumed by `SalesTeamScopeService`, Coordinator lead
  and agenda monitoring, Daily Plan submission notifications, Coordinator team
  authority, Sales fee/reporting views, and consumer handoff metadata.
- Admin-user creation explicitly describes the reporting relationship as not being the
  source of Team Sales authorization.
- RBAC documentation explicitly states that reporting hierarchy does not create
  Coordinator TEAM authority.
- Sales lead freelance conversion uses the active Supervisor relationship for the
  normal Coordinator handoff, while allowing a Coordinator fallback only when no valid
  Supervisor exists.
- `OrganizationGraphService` currently collapses the two dimensions when a Sales user
  is assigned to a Coordinator because its `reports_to` writer projects Coordinator
  membership. This is the canonical-model defect to correct.

Therefore the four observed users are not four unresolved parent-choice conflicts.
They are four examples of two valid simultaneous relationships:

```text
Sales user  --reports_to----------> Supervisor 13
Sales user  --sales_team_member_of-> Coordinator 12
```

## Goals

- Define the smallest OASIS-specific canonical relationship taxonomy.
- Represent formal reporting and operational Sales membership independently.
- Allow both relationships to be active for one Sales user.
- Keep reporting traversal separate from Sales-team traversal.
- Make parity compare like relationship types against like relationship types.
- Make backfill deterministic and non-destructive for both legacy sources.
- Preserve branch/project workspace boundaries and permission-based authority.
- Prove that orthogonal relationships do not create an authorization union.

## Non-goals and anti-goals

- No graph cutover or `graph_mode` change.
- No Phase 3 work.
- No deletion of `supervisor_user_id` or `sales_coordinator_sales`.
- No role or permission redesign.
- No route, navigation, or broad UI restructuring.
- No automatic granting of authority from a relationship alone.
- No global/write backfill execution.
- No generic enterprise organization framework beyond OASIS relationships.

## Approaches Considered

### 1. Typed canonical edges — selected

Reuse `organization_assignments.relationship_type` with explicit relationship values.
Keep the existing table and audit/history model, but give each relationship type its
own cardinality, validation, current scope, and traversal methods. This is additive and
avoids introducing a second canonical assignment architecture.

### 2. Separate canonical Sales-team table

Keep `organization_assignments` exclusively for reporting and create a new canonical
table for Sales Coordinator membership. This is semantically clear but duplicates the
existing typed-edge capability and creates another writer, history model, parity path,
and compatibility surface.

### 3. Documentation/parity-only

Declare the legacy relationships orthogonal without changing the graph model. This
would avoid writes but leave canonical graph mode unable to represent the proven
four-user shape; it is insufficient for cutover preparation.

## Canonical Relationship Taxonomy

Phase 2.6 will support only these organization relationship types:

| Type | Source | Target | Existing source/evidence |
|---|---|---|---|
| `reports_to` | Any organizational user | Formal supervisor/manager parent | `users.supervisor_user_id`, `ReportingHierarchyService` |
| `sales_team_member_of` | Primary-role Sales user | Primary-role Sales Coordinator | `sales_coordinator_sales`, `SalesTeamScopeService` |
| Branch membership | User | Branch | `branch_user`, `WorkspaceAccessService`; remains workspace data |
| Project membership | User | Housing project | `project_user`, `WorkspaceAccessService`; remains assignment data |
| Historical relationship | Either supported relationship | Prior effective target | Existing assignment/mapping history with dates; not current access |

`reports_to` and `sales_team_member_of` are the only organization graph edges in this
phase. Branch/project membership are not converted into graph hierarchy edges.

## Relationship Semantics

### `reports_to`

- Direction: employee/user → formal parent.
- Allowed roles: validated by existing role-rank and graph hierarchy rules.
- Branch/workspace: existing shared workspace and organization-tree validation applies.
- Cardinality: at most one active primary reporting parent per user.
- Active/history: current assignment is date-valid and active; ended rows remain history.
- Reporting traversal: yes.
- Sales-team traversal: no.
- Generic module visibility: only through existing module permission/scope rules.
- Authority: no authority by edge alone.
- Navigation: no direct effect.
- Reporting/dashboard: formal management hierarchy and supervisor monitoring.

### `sales_team_member_of`

- Direction: Sales user → Sales Coordinator.
- Allowed roles: source primary role `sales`; target primary role
  `sales_coordinator`.
- Branch requirement: active primary branches must match, as enforced by
  `SalesCoordinatorAssignmentService`.
- Project requirement: no direct project edge requirement; resulting module queries
  still intersect the Sales user's and Coordinator's authorized workspace/project scope.
- Cardinality: one active current Coordinator per Sales user under the existing
  assignment service; one Coordinator may have many Sales users. Historical rows may
  retain prior Coordinators.
- Active/history: current mappings grant current Sales-team membership; ended mappings
  are historical only.
- Reporting traversal: no.
- Sales-team traversal: yes.
- Generic module visibility: no automatic effect on Work Planner, Database, Consumer
  Progress, Dana Talangan, Pengeluaran, or organization administration.
- Authority: only the explicit Coordinator permissions and module policy grant
  Coordinator authority; the edge alone grants none.
- Navigation: no direct effect.
- Reporting/dashboard: Coordinator Sales monitoring, Sales-team KPIs, agenda/lead
  visibility, Daily Plan notification targeting, and relevant handoff metadata.

### Workspace relationships

`branch_user` and `project_user` remain the authoritative workspace/assignment sources.
They constrain both relationship traversals but do not become reporting parents or Sales
Coordinator edges.

## Four Conflict Decisions

The four observed cases are classified as **A: both relationships are valid
simultaneously**:

| Sales user | `reports_to` | `sales_team_member_of` | Decision |
|---:|---:|---:|---|
| 11 | 13 | 12 | Both valid simultaneously |
| 21 | 13 | 12 | Both valid simultaneously |
| 22 | 13 | 12 | Both valid simultaneously |
| 23 | 13 | 12 | Both valid simultaneously |

This decision is supported by the separate executable consumers and explicit RBAC
documentation. No relationship is stale or replaced solely because the other exists.

## Graph Model Changes

The existing `relationship_type` column becomes semantically enforced rather than being
treated as one universal parent hierarchy:

- preserve `reports_to` behavior and current `OrganizationAssignment::current()` API
  for compatibility;
- add relationship-specific scopes and accessors for `sales_team_member_of`;
- add relationship-specific graph writer methods rather than routing both meanings
  through `assign()`;
- stop treating a Coordinator parent on a reporting edge as proof of Sales-team
  membership;
- preserve audit history, effective dates, branch/project context, and compatibility
  projections;
- avoid restrictive database constraints until existing data is measured.

The graph service must not permit a Sales-team edge to participate in cycle detection
or formal reporting parent resolution. Reporting cycle checks operate only on
`reports_to` edges.

## Traversal Behavior

### Reporting traversal

`ReportingHierarchyService`, `OrganizationScopeService::hierarchyIds()`, formal
descendant queries, supervisor monitoring, and management hierarchy use only current
`reports_to` edges or their preserved legacy projection while production remains in
legacy mode.

### Sales-team traversal

`SalesTeamScopeService`, Coordinator lead/agenda monitoring, Coordinator policy checks,
Daily Plan notification targeting, and Sales-team reporting use only current
`sales_team_member_of` edges or their preserved `sales_coordinator_sales` projection
while production remains in legacy mode.

A user reached through reporting does not automatically become a Coordinator's Sales
team member. A Sales-team member does not automatically become a reporting descendant.

## Role Semantics

| Role | Reporting hierarchy | Sales-team relationship | Operational assignment | System administration |
|---|---|---|---|---|
| `sales` | May have one parent | May belong to one active Coordinator | Own/project assignment | No |
| `sales_coordinator` | May report to Supervisor/Manager according to hierarchy | Owns current mapped Sales team | Explicit Sales-team permissions | No |
| `supervisor` | Formal management parent | May monitor through module permissions and hierarchy | Branch/team scope as authorized | No |
| `manager` | Formal management parent | May see mapped teams through authorized reporting path | Branch/project scope | No |
| `branch_manager` | Formal management parent | May see mapped teams through authorized reporting path | Branch operations | No |
| `sas` / `sam` | Role-specific formal hierarchy where assigned | No automatic Coordinator authority | Explicit module permissions | No |
| `pusat` | Explicit organizational relationships where assigned | No automatic Coordinator authority | Explicit mapped permissions | No |
| `admin` / `staff` | Compatibility/formal relationships where assigned | No automatic Coordinator authority | Explicit permissions | No automatic system authority |
| `superadmin` | May administer graph subject to system policy | May administer mappings subject to system policy | Full registered permissions | Yes |

Role labels do not create relationships or permissions by themselves.

## Parity and Backfill Rules

Parity compares like dimensions:

- `users.supervisor_user_id` ↔ canonical `reports_to`;
- `sales_coordinator_sales` ↔ canonical `sales_team_member_of`;
- branch membership ↔ `branch_user`;
- project assignment ↔ `project_user`.

The four users must no longer be reported as a parent conflict when both typed edges
exist. A missing `reports_to` edge and a missing Sales-team edge remain separate,
actionable mismatches.

Backfill maps independently:

1. legacy `supervisor_user_id` → `reports_to`;
2. current `sales_coordinator_sales` → `sales_team_member_of`;
3. historical rows → historical typed edge with effective dates;
4. duplicate, invalid, cross-tree, or ambiguous same-type relationships remain
   classified and are not guessed.

Backfill remains dry-run capable, idempotent, auditable, and non-destructive. No global
write backfill is authorized in Phase 2.6.

## Access Safety

Relationship edges do not grant permissions. Every module still requires explicit
permission, workspace access, organization scope, and target policy checks.

The tests must prove that Sales-team membership does not expand access to Consumer
administration, Finance, Organization administration, or system administration, and
that reporting membership does not create Coordinator mutation authority.

## Cutover Gate

The gate remains blocked until all supported typed dimensions have parity:

- unknown mismatches: zero;
- access expansion: zero;
- unresolved critical access loss: zero;
- cross-branch/project leakage: zero;
- unresolved Sales-team mapping conflict: zero;
- unresolved reporting conflict: zero;
- cycle failures: zero;
- backfill idempotency failures: zero.

Even if the gate becomes ready, Phase 2.6 does not authorize graph cutover or Phase 3.
